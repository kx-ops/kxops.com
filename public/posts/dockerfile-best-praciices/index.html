Dockerfile 实践 以安全为核心的镜像构建

May 12, 2026

Dockerfile 是容器镜像的"源代码"，其质量直接决定了运行时容器的攻击面。一个随意编写的 Dockerfile 可能让容器以 root 身份运行、嵌入敏感凭证、打包大量无用工具，使单一漏洞迅速演变为横向入侵。本文从安全视角出发，结合生产实践，总结 Dockerfile 编写的关键原则与落地示例。

一、选择最小、可信的基础镜像#

基础镜像是继承自上游的一切漏洞的源头。越臃肿的镜像，潜在 CVE 越多。

  1. 优先使用官方或经过验证的镜像：如 python:3.12-slim、node:20-alpine、golang:1.22-alpine
  2. 优选 distroless 或 scratch：Google 的 gcr.io/distroless/* 不包含 shell、包管理器，攻击面最小
  3. 固定 tag 并校验摘要：使用 image@sha256:... 锚定内容，防止 tag 被悄悄替换
  4. 避免使用 latest：不可复现，且存在供应链被污染的风险
# 不推荐
FROM ubuntu:latest

# 推荐：固定版本 + 摘要
FROM python:3.12-slim@sha256:a1b2c3d4e5f6...

# 更佳：distroless 运行时
FROM gcr.io/distroless/python3-debian12:nonroot

二、多阶段构建，剥离构建依赖#

编译工具链（gcc、make、git、npm）不应出现在最终镜像中。多阶段构建让构建期与运行期彻底隔离。

# 构建阶段
FROM golang:1.22-alpine AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /out/app ./cmd/app

# 运行阶段：仅包含二进制
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /out/app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]

这样最终镜像只包含二进制文件，不含 shell、包管理器或源代码，极大压缩了攻击者的可用空间。

三、以非 root 用户运行#

默认情况下容器以 root 身份运行，一旦被突破即可能危及宿主。显式降权是强制要求。

# 创建专用用户
RUN addgroup --system --gid 1001 appgroup \
 && adduser --system --uid 1001 --ingroup appgroup appuser

# 拷贝文件并设置所有权
COPY --chown=appuser:appgroup ./app /home/appuser/app

USER appuser
WORKDIR /home/appuser

运行时同样建议配合 --read-only、--cap-drop=ALL、--security-opt=no-new-privileges 强化隔离。

四、严禁在镜像中嵌入敏感信息#

镜像的每一层都是可提取、可回溯的。任何写入镜像的密钥终将泄露。

  1. 构建期秘密：使用 BuildKit 的 --mount=type=secret
  2. 运行期秘密：通过环境变量、K8s Secret、Vault 等外部注入
  3. 私有仓库凭证：使用 --mount=type=ssh 而非 COPY 私钥
  4. 警惕层缓存：即便后续 RUN rm 删除，早期层中的文件仍然可被查看
# syntax=docker/dockerfile:1.7

# 构建期访问 npm 私服 token，不落入镜像层
RUN --mount=type=secret,id=npm_token,target=/root/.npmrc \
    npm ci --omit=dev

可通过 docker history 和 dive 工具审计镜像层，验证是否存在敏感数据残留。

五、合理排序指令，优化缓存与体积#

Docker 按指令生成层并缓存。变化频繁的指令越靠后，缓存命中率越高。

FROM python:3.12-slim AS runtime

# 系统依赖几乎不变，放最前
RUN apt-get update \
 && apt-get install -y --no-install-recommends ca-certificates tini \
 && rm -rf /var/lib/apt/lists/*

# 依赖文件变化较少
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 源码变化频繁，放最后
COPY . .

几点细节：

  1. apt-get update 必须与 apt-get install 放在同一 RUN 中，避免陈旧索引
  2. --no-install-recommends 减少无关包
  3. 清理 /var/lib/apt/lists/*、pip 缓存、npm 缓存
  4. 使用 .dockerignore 排除 .git、.env、node_modules、测试数据

六、显式声明运行时元数据#

元数据帮助运维与安全审计快速定位镜像来源。

LABEL org.opencontainers.image.source="https://github.com/org/app" \
      org.opencontainers.image.revision="${GIT_SHA}" \
      org.opencontainers.image.version="1.4.2" \
      org.opencontainers.image.licenses="Apache-2.0"

EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD ["/app", "healthcheck"]

ENTRYPOINT ["/sbin/tini", "--"]
CMD ["/app"]

使用 ENTRYPOINT + CMD 的 exec 形式可避免 shell 解析带来的注入风险，并让信号正确传递（配合 tini 处理僵尸进程）。

七、将安全检查纳入 CI 流水线#

Dockerfile 的安全性不能只依赖作者自觉，必须让工具在流水线中把关。

  1. 静态分析：hadolint 检查 Dockerfile 规范与反模式
  2. 漏洞扫描：trivy、grype 扫描 OS 包与语言依赖 CVE
  3. SBOM 生成：syft 输出 SPDX/CycloneDX 软件物料清单
  4. 镜像签名：cosign 配合 Sigstore 验证供应链完整性
  5. 策略强制：集群侧使用 Kyverno / OPA Gatekeeper 拒绝未签名或高危镜像
hadolint Dockerfile
trivy image --severity HIGH,CRITICAL --exit-code 1 myapp:1.4.2
syft myapp:1.4.2 -o spdx-json > sbom.json
cosign sign --key cosign.key myapp:1.4.2

八、一个整合示例#

将上述原则整合到一个生产级 Python 服务的 Dockerfile：

# syntax=docker/dockerfile:1.7

ARG PYTHON_VERSION=3.12.3
FROM python:${PYTHON_VERSION}-slim AS builder

ENV PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1 \
    PYTHONDONTWRITEBYTECODE=1

WORKDIR /build
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --prefix=/install -r requirements.txt

FROM python:${PYTHON_VERSION}-slim AS runtime

RUN apt-get update \
 && apt-get install -y --no-install-recommends tini ca-certificates \
 && rm -rf /var/lib/apt/lists/* \
 && addgroup --system --gid 1001 app \
 && adduser --system --uid 1001 --ingroup app app

COPY --from=builder /install /usr/local
WORKDIR /app
COPY --chown=app:app . .

USER app
EXPOSE 8080
ENTRYPOINT ["/usr/bin/tini", "--"]
CMD ["python", "-m", "app.main"]

HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8080/healthz')" || exit 1

九、安全清单#

发布前对照检查：

  1. 基础镜像是否固定版本并尽可能精简
  2. 是否使用多阶段构建剥离编译依赖
  3. 是否以非 root 用户运行
  4. 是否存在硬编码密钥、token、证书
  5. 是否清理了包管理器缓存与临时文件
  6. 是否提供 .dockerignore 并排除敏感文件
  7. 是否配置 HEALTHCHECK 与 LABEL 元数据
  8. CI 是否完成 hadolint / trivy / cosign 检查
  9. 是否生成并归档 SBOM
  10. 集群侧是否启用签名校验与准入策略

总结#

Dockerfile 应把"最小权限、最小体积、最小信任"当作默认选项，再辅以 CI 的自动化扫描与签名，能把容器化的安全债压在最低。安全不是写完 Dockerfile 后再补的附加项，而是从 FROM 第一行就开始的用心选择。
